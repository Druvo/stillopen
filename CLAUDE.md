# StillOpen: notes for Claude Code

Django 5.2 app: job-search dashboard, admin-configurable, with an MCP server. See README.md for features.

## Commands

```bash
python manage.py migrate
python manage.py test                      # runs everything, ~10 s; set STILLOPEN_DB=db_test.sqlite3 to keep your real DB out of it
python manage.py import_careerops          # career-ops tracker, reports, PDFs
python manage.py check_liveness            # open/closed check
python manage.py evaluate_jobs             # unscored roles only
python manage.py send_followup_emails      # daily digest of newly-due follow-ups; off by default (SiteConfig.followup_emails_enabled)
python mcp_server.py                       # MCP server over stdio
```

## Layout

- `tracker/models.py`: SiteConfig (singleton, all settings), Application, Status/Bucket/ScoreBand/... (config tables seeded by migration 0002)
- `tracker/services/`: `careerops.py` (import), `liveness.py` (open/closed), `scan.py` (zero-token job search over JobSource -- single-company boards Greenhouse/Lever/Ashby/SmartRecruiters/Recruitee, and multi-employer aggregators RemoteOK/We Work Remotely/Himalayas/Remotive/Arbeitnow/Jobicy/Working Nomads/The Muse; ~100 sources are seeded by migration 0031 from `tracker/seed_sources.py` (skipped under `manage.py test`, `settings.STILLOPEN_SEED_SOURCES`; `REGIONAL` + `JOOBLE` lists cover Malaysia/Gulf/Bangladesh and are added to existing installs once by migration 0033; Jooble is a keyed *search* connector (`SiteConfig.jooble_api_key` / `JOOBLE_API_KEY`, write-only), asked with each person's own roles per country, skipped without a key, never read from a worker thread's DB -- the key is passed in), and `scan.maybe_auto_start` searches for a person when they open the dashboard and their last search is older than `SiteConfig.auto_scan_hours`. The worker reads all sources in parallel (`_prefetch`, hard deadline, shared cache), records sightings in bulk, drops postings that `fit.clearly_outside` the person's search areas (unknown is never excluded), dedupes the same job across sources, scores new jobs with the free keyword match, and adds the global top `STILLOPEN_SCAN_MAX_NEW` ranked clear-fit first; title-matched against target_roles, with a fallback skill-overlap match (candidate's own CV/knowledge terms vs. a posting's title+description, STILLOPEN_SKILL_MATCH_MIN_OVERLAP shared terms -- surfaced as an Event note and a "Skill match" dashboard badge) for a posting whose title misses every target-role phrase, dedup by URL; also records every posting seen as a `Posting`/`PostingSighting`, shared across users, keyed on company+title so an aggregator's many employers never cross-contaminate, and flags a repost pattern -- 2+ distinct URLs on 2+ distinct scan dates for the same company+title, same discipline as career-ops' detect-reposts.mjs, an observation never a verdict. Checked and not added: Workable (its public job-board API returned empty for every real company tried -- looks sunset), LinkedIn (ToS/anti-bot -- paste a URL into Add job instead), bdjobs.com and Canada's Job Bank open-data CSV (no usable live API: the former needs a headless browser, the latter is a 44MB monthly dump whose own server times out on a plain download)), `ai.py` (providers, prompt, keyword fallback; every paid-provider call logs an `AIUsageEvent` -- tokens from the provider's own response, cost either reported directly (Claude Code CLI/Agent SDK) or estimated from a small static per-model price table, never a guess for an unpriced model; never logged for the free keyword match, which makes no network call. Usage is captured via a module-level `contextvars.ContextVar` each backend sets right before returning, read once by `evaluate_application`/`complete()` -- keeps every backend's plain str-in/str-out signature unchanged. Surfaced as a monthly total on Profile -> AI settings and appended to each evaluation's Event note. The same page's "Quick setup" dropdown (`templates/tracker/profile_ai.html`, pure client-side JS, no new field) fills the "openai" provider's base URL + a starting model for 8 popular OpenAI-compatible endpoints (Gemini, Groq, Mistral, DeepSeek, OpenRouter, GLM/Zhipu...) plus Anthropic direct -- Ollama/LM Studio only for staff, since local URLs are already admin-only at the model layer), `knowledge.py` (candidate knowledge base, chunking, BM25/embeddings retrieval), `text.py` (shared tokenizer), `jobtext.py` (guarded URL fetch), `paperless.py`
- `tracker/services/`: also `cvgen.py` (tailoring: AI or keyword), `cvversions.py` (immutable history, restore, approve), `factcheck.py` (flags claims not in the person's material), `cvexport.py` (Markdown to safe HTML, DOCX, diff); views in `tracker/views_cv.py`, `apply.py` (apply assistant: checklist, record, follow-ups, email draft; `send_followup_digest`/`due_followups_to_email` send one digest email per person per run for newly-due follow-ups -- never one email per job, never a repeat for the same `follow_up_date` thanks to `Application.follow_up_emailed_for`, requires a verified allauth email address, gated by `SiteConfig.followup_emails_enabled` -- see `manage.py send_followup_emails`); `geo.py` (places, regions, cities and detection from posting text); `fit.py` (checks a job against search areas, pay, type, seniority); views in `tracker/views_apply.py`
- `views.quickadd_fetch`/`views.add_job`: the dashboard's "Paste a job URL" bar fetches title+description
  (`services/jobtext.fetch_posting`, `guess_role_company`) and hands them to the add-job form via the
  session (`request.session["quickadd_prefill"]`, popped on the next GET) -- never via a query string, since
  a full job description would routinely exceed the URL length browsers/servers accept. Nothing is saved
  until the person reviews and submits the normal add-job form; the title-split guess is best-effort and
  often wrong, which is why there's a review step, not an auto-save.
- `views.all_postings`/`views.add_posting` (`templates/tracker/postings.html`): browsable, paginated, search/source-filterable list of every `Posting` ever seen (shared, like the model itself) with a per-viewer "Tracked"/"Add to tracker" state computed from that viewer's own `Application.url`s -- the read-mostly answer to "it found 586 but only tracked 11, where did the rest go".
- `tracker/views_pipeline.py` (+ `Interview`, `Contact`, `Referral`, `Offer` in models.py; forms in forms.py; templates `interviews.html`/`contacts.html`/`offers.html`): the stage after "Applied". All owner-scoped; the forms limit every job/contact choice to the owner's own rows (`OwnedFormMixin`). Offers are compared per currency, never converted. Tests in `tracker/tests_pipeline.py` (isolation included).
- `tracker/mcp_tools.py`: plain functions behind the MCP tools; `mcp_server.py` registers them
- `tracker/auth.py`: allauth adapters (Google sign-in gated by an allowlist)
- `.claude/skills/stillopen/SKILL.md`: how an AI should use the MCP tools
- UI is Tabler (Bootstrap 5, CDN, no build step) via `templates/tracker/base_app.html` (sidebar) and `templates/allauth/layouts/base.html` (sign-in pages). `tracker/templatetags/form_tags.py`'s `bootstrap_field` filter adds `form-control`/`form-select`/`form-check-input` to bare `{{ field }}` renders. `FORM_RENDERER = TemplatesSetting` in settings.py (plus `django.forms` in INSTALLED_APPS) makes Django's own widget templates resolvable under project `TEMPLATES[0]["DIRS"]` -- needed for the `templates/django/forms/widgets/multiple_input.html`/`input_option.html` overrides, which wrap each CheckboxSelectMultiple/RadioSelect option in Bootstrap's required `.form-check` div (the default renderer ignores DIRS entirely and Bootstrap's checkbox/radio CSS breaks without that wrapper).

## Rules

- **Multi-user, strict isolation.** Every Application, KnowledgeSource, Document, Event, LivenessRun and UserProfile belongs to one user. Every view, command and MCP tool must filter by owner (`owner=request.user`, `who.resolve_user`, `mcp_tools._owner()`); cross-account access must 404. New data model or endpoint = owner field/filter + a test in `tracker/tests_multiuser.py`. **Deliberate exception:** `Posting`/`PostingSighting` (repost/ghost-job detection, `scan.py`) have no owner -- they key on `(JobSource, url)`, which is a fact about the company's board, not about any one person's search, so they're shared across every user watching that source by design. `Application.posting` only links a user's own matched row to that shared fact; it never exposes another user's `Application`.
- Per-person settings come from `SiteConfig.for_user(user)` (read-only overlay of `UserProfile`, never saved). Server-touching features (career-ops folder, Paperless, `claude_cli`/`agent_sdk`, local model URLs, node checker) are admin-only: `config.restricted` is True for ordinary users.
- Any URL a user can supply (job links, AI base URLs, embedding URLs) must go through `services/netguard.py` (`check_public_url` / `safe_get`) for restricted users; AI POSTs use `allow_redirects=False`.
- `JobSource` (which company boards `scan.py` searches) has two kinds. **Site-wide** (`owner` null): admin-only, registered only in Django admin, searched for everyone; aggregators (RemoteOK, We Work Remotely, Himalayas) are always this kind. **A person's own** (`owner` set, `views_sources.py`, `/sources/`): single-company connectors only (`JobSource.OWN_CONNECTORS`). A person supplies only a connector from that fixed list and a token (`forms.OwnSourceForm`: starts alphanumeric, no dots or slashes, 60 chars; a pasted careers-page address is only *parsed* for its token, never fetched); the app builds the URL on the connector's fixed host and the first fetch uses `scan._fetch` -> `safe_get`. Capped (`STILLOPEN_MAX_OWN_SOURCES`) and rate-limited (`STILLOPEN_SOURCE_ADDS_PER_HOUR`). Every read of sources and postings must go through `JobSource.for_user(user)` (site-wide + own, never anyone else's): the scan worker, `start_run`, the dashboard, All postings and add-posting all do. A scan only ever creates `Application` rows owned by the person who clicked the button, filtered by their own `target_roles` and deduplicated by URL -- it never touches another user's data. Tests in `tracker/tests_sources.py`.
- Self-registered accounts must confirm their email (`AccountAdapter.pre_login`); accounts made by admins or `createsuperuser` must never be locked out.
- **First-run flow and voice.** Sign-up asks for email + password only (the username is derived). The confirmation link is the whole sign-up: the first click verifies, signs in (`signals.sign_in_after_first_confirmation`, only for self-registered people and only when that click did the verifying) and lands on `/welcome/`, a skippable three-question page (`UserProfile.onboarding_done`). New jobs start as `Saved` and become `Evaluated` when their fit is checked. Copy that a person reads speaks to them directly in plain words: no jargon (`evaluate`, `provider`, `RAG`), no harsh labels (the lowest score band is "A stretch", not "Weak"), no raw `N/A`, and every empty state says what to do next. `services/guide.py` picks the one next step shown on the dashboard.

- Behaviour must stay configurable in the admin, not hard-coded. New setting = SiteConfig field + migration + admin fieldset + test.
- Job descriptions are untrusted text. Never put them where they could act as instructions: keep them in data tags, validate model output, never give a model tools while it reads one.
- Never log or display secrets. The AI key is stored encrypted (`tracker/crypto.py`); Paperless token and keys never appear in MCP output.
- MCP surface is deliberately small: no delete tool, no settings/keys/file access. Keep it that way.
- The keyword fallback must never overwrite an existing score.
- Tests that touch SiteConfig should clear `careerops_path` (use `isolated_config` in `tests_ai.py`) so they never read a developer's real career-ops folder.
- Use `python manage.py makemigrations` after model changes; commit the migration.
- CV versions are immutable (`CVVersion.save` refuses content changes). A tailored version with flagged claims must stay un-exportable until the person approves it; MCP/AI clients may never approve. Never render CV Markdown without `cvexport.to_html` (it escapes everything).
- The app never submits an application or sends a message. `apply.record` only records what the person did; it must refuse CV versions that are flagged and unapproved, another person's, or tailored for a different job. `Application.applied_cv` is RESTRICT so a sent CV cannot be deleted on its own (account and application deletion still cascade).
- Location logic lives in `geo.py` and `fit.py` only. A place that cannot be resolved must stay unknown (never guessed), detection only fills blank fields and never overwrites `details_source == "manual"`, and a fit check flags a job but never hides one. A remote job limited to one country fits only if the person lives there (`home_country`) or an area names that country.
- No page may load a stylesheet, script, font or image from a third-party host (tests in `tracker/tests_selfhost.py`). Front-end files are vendored under `static/vendor/` with their licence banner and verified hashes (see `static/vendor/tabler/NOTICE.md`) and served by WhiteNoise. Do not add a CDN `<link>`/`<script>`; vendor the file instead. The admin theme's Google Fonts CDN is turned off.
