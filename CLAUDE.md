# StillOpen: notes for Claude Code

Django 5.2 app: job-search app, admin-configurable, with an MCP server. See README.md for features.

## Commands

```bash
python manage.py migrate
python manage.py test                      # runs everything, ~10 s; set STILLOPEN_DB=db_test.sqlite3 to keep your real DB out of it
python manage.py import_careerops          # career-ops tracker, reports, PDFs
python manage.py check_liveness            # open/closed check
python manage.py evaluate_jobs             # unscored roles only
python manage.py send_followup_emails      # daily digest of newly-due follow-ups; off by default (SiteConfig.followup_emails_enabled)
python mcp_server.py                       # MCP server over stdio
```

## Layout

- `tracker/models.py`: SiteConfig (singleton, all settings), Application, Status/Bucket/ScoreBand/... (config tables seeded by migration 0002)
- `tracker/services/`: `careerops.py` (import), `liveness.py` (open/closed), `scan.py` (zero-token job search over JobSource -- single-company boards Greenhouse/Lever/Ashby/SmartRecruiters/Recruitee, and multi-employer aggregators RemoteOK/We Work Remotely/Himalayas/Remotive/Arbeitnow/Jobicy/Working Nomads/The Muse; ~100 sources are seeded by migration 0031 from `tracker/seed_sources.py` (skipped under `manage.py test`, `settings.STILLOPEN_SEED_SOURCES`; `REGIONAL` + `JOOBLE` lists cover Malaysia/Gulf/Bangladesh and are added to existing installs once by migration 0033; Jooble is a keyed *search* connector (`SiteConfig.jooble_api_key` / `JOOBLE_API_KEY`, write-only), asked with each person's own roles per country, skipped without a key, never read from a worker thread's DB -- the key is passed in; `context.staff_flags`'s `jooble_sources_dormant` nudges a staff member with a dashboard banner when a site-wide Jooble source is enabled but no key is set, since `fetch_jooble` otherwise just silently returns nothing every search), and `scan.maybe_auto_start` searches for a person when they open the dashboard and their last search is older than `SiteConfig.auto_scan_hours`. The worker reads all sources in parallel (`_prefetch`, hard deadline, shared cache), records sightings in bulk, drops postings that `fit.clearly_outside` the person's search areas (unknown is never excluded), dedupes the same job across sources, scores new jobs with the free keyword match, and adds the global top `STILLOPEN_SCAN_MAX_NEW` ranked clear-fit first; title-matched against target_roles, with a fallback skill-overlap match (candidate's own CV/knowledge terms vs. a posting's title+description, STILLOPEN_SKILL_MATCH_MIN_OVERLAP shared terms -- surfaced as an Event note and a "Skill match" dashboard badge) for a posting whose title misses every target-role phrase, dedup by URL; also records every posting seen as a `Posting`/`PostingSighting`, shared across users, keyed on company+title so an aggregator's many employers never cross-contaminate, and flags a repost pattern -- 2+ distinct URLs on 2+ distinct scan dates for the same company+title, same discipline as career-ops' detect-reposts.mjs, an observation never a verdict. Checked and not added: Workable (its public job-board API returned empty for every real company tried -- looks sunset), LinkedIn (ToS/anti-bot -- paste a URL into Add job instead), Canada's Job Bank open-data CSV (a 44MB monthly dump whose own server times out on a plain download). bdjobs.com's own *listing pages* are a client-side app with nothing server-rendered, but `fetch_bdjobs` wires in its undocumented internal JSON search API instead (found via the site's own network traffic, verified live, no headless browser or cookies needed) -- the one deliberate exception to "no scraping, only documented/public feeds": bdjobs.com's robots.txt disallows generic bots (`Disallow: /` except for named crawlers), so this ships OFF by default, seeded nowhere, an explicit opt-in an admin adds themselves. `fetch_bikroy` is the same kind of exception for a different reason: bikroy.com's Jobs category *is* server-rendered (Nuxt 3), so a plain GET already returns every posting, just embedded in the page's own `__NUXT_DATA__` hydration script (devalue-style array-of-references) rather than a clean JSON body -- decoded by a small generic resolver (`_nuxt_resolve`) rather than a library. Its own robots.txt does not disallow this path for generic bots. Also ships OFF by default, also an admin's own opt-in. `fetch_usajobs` is the opposite case: USAJOBS, the US federal job board, publishes and supports a real documented public Search API, no robots.txt trade-off at all -- just a free key plus the email it was requested with (`SiteConfig.usajobs_api_key`/`usajobs_email`, both env-overridable, both required -- USAJobs requires the email as the `User-Agent` header on every call; `usajobs_sources_dormant` nudges staff the same way `jooble_sources_dormant` does). Ships OFF by default like the others, since it needs that key to do anything), `ai.py` (providers, prompt, keyword fallback; every paid-provider call logs an `AIUsageEvent` -- tokens from the provider's own response, cost either reported directly (Claude Code CLI/Agent SDK) or estimated from a small static per-model price table, never a guess for an unpriced model; never logged for the free keyword match, which makes no network call. Usage is captured via a module-level `contextvars.ContextVar` each backend sets right before returning, read once by `evaluate_application`/`complete()` -- keeps every backend's plain str-in/str-out signature unchanged. Surfaced as a monthly total on Profile -> AI settings and appended to each evaluation's Event note. The same page's "Quick setup" dropdown (`templates/tracker/profile_ai.html`, pure client-side JS, no new field) fills the "openai" provider's base URL + a starting model for 8 popular OpenAI-compatible endpoints (Gemini, Groq, Mistral, DeepSeek, OpenRouter, GLM/Zhipu...) plus Anthropic direct -- Ollama/LM Studio only for staff, since local URLs are already admin-only at the model layer), `knowledge.py` (candidate knowledge base, chunking, BM25/embeddings retrieval), `text.py` (shared tokenizer), `jobtext.py` (guarded URL fetch), `paperless.py`
- `tracker/services/`: also `cvgen.py` (tailoring: AI or keyword), `cvbuilder.py` (`POST /api/v1/cv/build` + `frontend` `/cv/build`: a short guided Q&A that assembles a first CV for someone with nothing to paste yet -- no AI, nothing beyond what was typed; empty sections are omitted rather than rendered with invented filler; saves through the same `cvversions.record_master` path as pasting a CV by hand, so RAG/matching/tailoring pick it up identically), `cvversions.py` (immutable history, restore, approve), `factcheck.py` (flags claims not in the person's material), `cvexport.py` (Markdown to safe HTML, DOCX, diff; `TEMPLATES`/`to_docx(markdown, template=...)`: three built-in, font/colour-only looks -- classic/modern/compact, never a table/column/image since those break ATS parsers -- picked via `?template=` on the download and print URLs, validated in `views_cv.py`, an unknown name quietly falls back to `DEFAULT_TEMPLATE` ("classic", byte-for-byte the original look)); the CV download and print views are in `tracker/views_cv.py` (cover letters: `views_cover.py`), the screens in the app; `apply.py` (apply assistant: checklist, record, follow-ups, email draft; `send_followup_digest`/`due_followups_to_email` send one digest email per person per run for newly-due follow-ups -- never one email per job, never a repeat for the same `follow_up_date` thanks to `Application.follow_up_emailed_for`, requires a verified allauth email address, gated by `SiteConfig.followup_emails_enabled` -- see `manage.py send_followup_emails`); `geo.py` (places, regions, cities and detection from posting text); `fit.py` (checks a job against search areas, pay, type, seniority); `techskills.py` (`recognized()`: real named technologies -- Docker, Kubernetes, React... -- a posting mentions, each marked whether the owner's own CV/knowledge covers it; catalog bundled at `tracker/data/onet_tech_skills.json`, 8,741 names deduplicated from the US Department of Labor's O*NET `software_skills.csv`, CC BY 4.0, live-checked as a good fit where ESCO was live-checked and rejected -- see `docs/ROADMAP.md`; wired into `services/cards.py::card_for` as `tech_skills`, computed from a `candidate_text` the one caller, `/api/v1/dashboard`, reads once rather than once per card); `languagetool.py` (`check()`: optional self-hosted grammar/clarity check for CV and cover letter text -- `SiteConfig.languagetool_url`/`LANGUAGETOOL_URL`, off (nothing sent anywhere) while blank, a URL is the opt-in rather than a separate enable switch; `POST /api/v1/cv/{id}/writing-check` and `/cover/{id}/writing-check`, owner-scoped, rate-limited via `STILLOPEN_CHECKS_PER_HOUR`; `writing_check_enabled` on `/me` gates the frontend's "Check writing" button); `libretranslate.py` (`translate()`: optional self-hosted translation of a job's description -- `SiteConfig.libretranslate_url`/`LIBRETRANSLATE_URL`, same off-by-blank discipline as LanguageTool; `POST /api/v1/jobs/{id}/translate`, owner-scoped, rate-limited, result shown for reading only and never saved; `translate_enabled` on `/me`)
- Quick add (`POST /api/v1/quickadd`, `api/jobs.py`): the app's "Paste a job URL" bar fetches title+description (`services/tracking.fetch_prefill`, `jobtext.fetch_posting`, `guess_role_company`) and fills the add-job form; nothing is saved until the person reviews and submits it, and the title-split guess is best-effort, which is why there is a review step.
- All postings (`GET /api/v1/postings`, `api/jobs.py`): browsable, paginated, search/source-filterable list of every `Posting` ever seen (shared, like the model itself) with a per-viewer "Tracked"/"Add to tracker" state computed from that viewer's own `Application.url`s -- the read-mostly answer to "it found 586 but only tracked 11, where did the rest go".
- `tracker/api/preferences.py` + `services/preferences.py` (`UserProfile.ui_preferences`): how a person likes the app laid out (dashboard view, tab, sort, filters, sidebar, theme, text size, density), validated on write, always normalized on read, returned in `/me`. `tracker/api/stats.py` + `services/stats.py`: the candidate's own numbers (this week, eight-week activity, match quality, replies and waiting, sources, recurring skill gaps, prep, market) -- plain counts, owner-only, never predictions. `tracker/middleware.py`: gzip and ETag/304 for `/api/v1/` answers only (never pages: BREACH).
- `tracker/api/pipeline.py` + `services/pipeline.py` (+ `Interview`, `Contact`, `Referral`, `Offer` in models.py; forms in forms.py): the stage after "Applied". All owner-scoped; the forms limit every job/contact choice to the owner's own rows (`OwnedFormMixin`). Offers are compared per currency, never converted. `funnel()` also backs the Insights page's `by_score` (match-band calibration), `monthly_trend`, and `rejection_patterns` (gap terms the free keyword match flagged on more than one rejected job -- only its own fixed "Your CV doesn't mention: X" phrasing is counted, never an AI's free-form wording, which can't be counted the same honest way). `weekly_counts`/`weekly_digest_text`/`send_weekly_digest` back the weekly digest email (`manage.py send_weekly_digest`, gated by `SiteConfig.weekly_digest_site_enabled` + `UserProfile.weekly_digest_enabled`/`weekly_digest_sent_through`, same two-level opt-in and verified-email requirement as `scheduled_scan`/`send_scan_digest`). Tests in `tracker/tests_pipeline.py` (isolation included), `tracker/tests_weekly_digest.py`.

- **Public side** (`views_public.py`, `services/public.py`, `landing_content.py`, `templatetags/charts.py`, `static/css/stillopen.css`, `static/js/theme.js`): landing page, `/openings/` board, per-opening pages, an RSS feed (`openings_feed`, same filters as the board, items link to our own credited page not straight to the source), robots.txt, sitemap. Rules that must hold: only `JobSource.show_publicly` site-wide sources (never `owner` set) and only `Posting`s seen within `STILLOPEN_PUBLIC_ACTIVE_DAYS`; a short `Posting.excerpt`, never the full text; every opening credits its source and links to the unchanged original; **no JobPosting JSON-LD** (Google needs the full description; Remotive and Himalayas forbid passing jobs to Google Jobs); gone openings answer 410; Remotive stays off (`seed_sources.PUBLIC_OK_CONNECTORS` is the allow-list, and any new source defaults to hidden). Charts are server-drawn inline SVG (escape every label). The look is light by default with a remembered dark toggle; no external fonts, scripts or images (tests in `tests_selfhost.py`).
- **Free, no-sign-in tools** (`views_tools.py`, templates `tools_*.html`, tests in `tests_public_tools.py`): a job-fit checker (`services/ai.keyword_match`), "is this job still open?" (`services/liveness.check_url`), and an offer comparator (two unsaved `Offer` instances reused through `services/pipeline.comparison()` unchanged). Nothing is saved; each POST is rate-limited per IP (`services/throttle.throttled_ip`/`client_ip`, `STILLOPEN_PUBLIC_TOOL_RATE_PER_HOUR`) since nobody is signed in to limit by account; each form uses `forms.HoneypotMixin` (same bot-trap discipline as sign-up -- a hidden field, a minimum fill time via `STILLOPEN_PUBLIC_TOOL_MIN_SECONDS`, no CAPTCHA).
- `tracker/legal.py`: the privacy/terms templates (`PRIVACY`, `TERMS`), the old defaults they replace, and `has_placeholders` (an admin banner shows while `[blanks]` remain and sign-up is open). `check_email`, `check_jooble`, `update_legal_text` are operator commands; `deploy/` holds the cron/Task Scheduler files and `.github/workflows/tests.yml` runs the suite in CI. `Application.description_is_excerpt` marks a search's short saved text, which `ai.ensure_description` upgrades to the full posting on first need.
- `tracker/mcp_tools.py`: plain functions behind the MCP tools; `mcp_server.py` registers them
- `tracker/auth.py`: allauth adapters (Google sign-in gated by an allowlist)
- `.claude/skills/stillopen/SKILL.md`: how an AI should use the MCP tools
- **Signed-in UI** is the Next.js static export in `frontend/`, served at `/app/` by `views_app.py` (login only; a plain 503 page when `frontend/out` is not built) on the JSON API at `/api/v1/` (`tracker/api/`, django-ninja; see `docs/design/nextjs-frontend.md`). The old classic candidate pages are gone: `tracker/legacy.py` redirects their addresses into `/app/...`. Only file and download views stay as Django views (`views.py`: `document_file`, `export_data`, privacy, terms, email test; `views_cv.py`/`views_cover.py`: downloads and the CV print page). Public pages, sign-in and admin pages use Tabler (Bootstrap 5, vendored, no build step) via `templates/tracker/public_base.html` and `templates/allauth/layouts/base.html`. `tracker/templatetags/form_tags.py`'s `bootstrap_field` filter adds `form-control`/`form-select`/`form-check-input` to bare `{{ field }}` renders. `FORM_RENDERER = TemplatesSetting` in settings.py (plus `django.forms` in INSTALLED_APPS) makes Django's own widget templates resolvable under project `TEMPLATES[0]["DIRS"]` -- needed for the `templates/django/forms/widgets/multiple_input.html`/`input_option.html` overrides, which wrap each CheckboxSelectMultiple/RadioSelect option in Bootstrap's required `.form-check` div (the default renderer ignores DIRS entirely and Bootstrap's checkbox/radio CSS breaks without that wrapper).

## Rules

- **Multi-user, strict isolation.** Every Application, KnowledgeSource, Document, Event, LivenessRun and UserProfile belongs to one user. Every view, command and MCP tool must filter by owner (`owner=request.user`, `who.resolve_user`, `mcp_tools._owner()`); cross-account access must 404. New data model or endpoint = owner field/filter + a test in `tracker/tests_multiuser.py`. **Deliberate exception:** `Posting`/`PostingSighting` (repost/ghost-job detection, `scan.py`) have no owner -- they key on `(JobSource, url)`, which is a fact about the company's board, not about any one person's search, so they're shared across every user watching that source by design. `Application.posting` only links a user's own matched row to that shared fact; it never exposes another user's `Application`.
- Per-person settings come from `SiteConfig.for_user(user)` (read-only overlay of `UserProfile`, never saved). Server-touching features (career-ops folder, Paperless, `claude_cli`/`agent_sdk`, local model URLs, node checker) are admin-only: `config.restricted` is True for ordinary users.
- Any URL a user can supply (job links, AI base URLs, embedding URLs) must go through `services/netguard.py` (`check_public_url` / `safe_get`) for restricted users; AI POSTs use `allow_redirects=False`.
- `JobSource` (which company boards `scan.py` searches) has two kinds. **Site-wide** (`owner` null): admin-only, registered only in Django admin, searched for everyone; aggregators (RemoteOK, We Work Remotely, Himalayas) are always this kind. **A person's own** (`owner` set, `api/sources.py`, `/app/sources`): single-company connectors only (`JobSource.OWN_CONNECTORS`). A person supplies only a connector from that fixed list and a token (`forms.OwnSourceForm`: starts alphanumeric, no dots or slashes, 60 chars; a pasted careers-page address is only *parsed* for its token, never fetched); the app builds the URL on the connector's fixed host and the first fetch uses `scan._fetch` -> `safe_get`. Capped (`STILLOPEN_MAX_OWN_SOURCES`) and rate-limited (`STILLOPEN_SOURCE_ADDS_PER_HOUR`). Every read of sources and postings must go through `JobSource.for_user(user)` (site-wide + own, never anyone else's): the scan worker, `start_run`, the app's job lists, All postings and add-posting all do. A scan only ever creates `Application` rows owned by the person who clicked the button, filtered by their own `target_roles` and deduplicated by URL -- it never touches another user's data. Tests in `tracker/tests_sources.py`.
- Self-registered accounts must confirm their email (`AccountAdapter.pre_login`); accounts made by admins or `createsuperuser` must never be locked out.
- **First-run flow and voice.** Sign-up asks for email + password only (the username is derived). The confirmation link is the whole sign-up: the first click verifies, signs in (`signals.sign_in_after_first_confirmation`, only for self-registered people and only when that click did the verifying) and lands on `/app/welcome`, a skippable three-question page (`UserProfile.onboarding_done`). New jobs start as `Saved` and become `Evaluated` when their fit is checked. Copy that a person reads speaks to them directly in plain words: no jargon (`evaluate`, `provider`, `RAG`), no harsh labels (the lowest score band is "A stretch", not "Weak"), no raw `N/A`, and every empty state says what to do next. `services/guide.py` picks the one next step shown on the dashboard.

- Behaviour must stay configurable in the admin, not hard-coded. New setting = SiteConfig field + migration + admin fieldset + test.
- Job descriptions are untrusted text. Never put them where they could act as instructions: keep them in data tags, validate model output, never give a model tools while it reads one.
- Never log or display secrets. The AI key is stored encrypted (`tracker/crypto.py`); Paperless token and keys never appear in MCP output.
- MCP surface is deliberately small: no delete tool, no settings/keys/file access. Keep it that way.
- The keyword fallback must never overwrite an existing score.
- Tests that touch SiteConfig should clear `careerops_path` (use `isolated_config` in `tests_ai.py`) so they never read a developer's real career-ops folder.
- Use `python manage.py makemigrations` after model changes; commit the migration.
- CV versions are immutable (`CVVersion.save` refuses content changes). A tailored version with flagged claims must stay un-exportable until the person approves it; MCP/AI clients may never approve. Never render CV Markdown without `cvexport.to_html` (it escapes everything).
- The app never submits an application or sends a message. `apply.record` only records what the person did; it must refuse CV versions that are flagged and unapproved, another person's, or tailored for a different job. `Application.applied_cv` is RESTRICT so a sent CV cannot be deleted on its own (account and application deletion still cascade).
- Location logic lives in `geo.py` and `fit.py` only. A place that cannot be resolved must stay unknown (never guessed), detection only fills blank fields and never overwrites `details_source == "manual"`, and a fit check flags a job but never hides one. A remote job limited to one country fits only if the person lives there (`home_country`) or an area names that country.
- No page may load a stylesheet, script, font or image from a third-party host (tests in `tracker/tests_selfhost.py`). Front-end files are vendored under `static/vendor/` with their licence banner and verified hashes (see `static/vendor/tabler/NOTICE.md`) and served by WhiteNoise. Do not add a CDN `<link>`/`<script>`; vendor the file instead. The admin theme's Google Fonts CDN is turned off.
